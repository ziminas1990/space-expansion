# SES-201: Extend IEngine so SetThrust returns an ACK with the ingame time the command was applied

## Problem

`change_thrust` (`SetThrust`) is fire-and-forget: the server applies thrust in `Engine::setThrust()` and sends no response.

The client therefore cannot tell:

- whether the command was accepted;
- at which ingame time thrust actually changed (the command may be delayed via `Message.timestamp`);
- which thrust value was applied (the server clamps `thrust` to `max_thrust`).

## Goal

The server must reply to `change_thrust` with an ACK. The ACK must include the **ingame time the command was applied**.

## Proposed behavior

1. The client sends `IEngine.change_thrust` as today (optionally with `Message.timestamp` as the desired apply time).
2. The server applies the command immediately or when that timestamp is reached.
3. After applying, the server sends an ACK on the same session.
4. The apply time (`uint64`, ingame clock microseconds) must be available to the client. If `Message.timestamp` is enough, document it as the ACK contract; otherwise add a field on the ACK body.

A delayed command must not be acknowledged on receipt: the ACK is sent only after the command is actually applied.

## Scope

- `server/Protocol.proto` — new `IEngine` response (e.g. `change_thrust_ack`).
- `server/Modules/Engine` — send ACK after apply.
- C++ ClientSDK and engine functional tests.
- Python SDK (`EngineI.set_thrust` / midlevel).
- TypeScript lowlevel/midlevel (`Engine.set_thrust` currently does not wait for a reply and blindly invalidates the thrust cache).
- `docs/API.ru/IEngine.md`.

## Acceptance criteria

- A successful `change_thrust` yields an ACK with the ingame apply time.
- For a command with a future `Message.timestamp`, the ACK time is the apply time, not the receive time.
- Existing clients that do not wait for a reply keep working (new `oneof` field).
- `IEngine` docs describe the ACK and the meaning of apply time.
