# SES-208: Add a RemoteControl module for tunneling to other ships by name

## Problem

Today a player reaches every owned ship by opening a tunnel on the **root
commutator**. That commutator is a player-level hub: every ship is attached to
it as a `BaseModule`, and `open_tunnel(slot)` is enough to talk to any of them,
regardless of where they are in the world.

That hub will not exist forever. A player connection will land on a single
ship's commutator. Reaching another ship will require an in-world module that
opens a tunnel to it, with a finite range and a finite number of simultaneous
links.

This task adds that module. It does **not** remove the root commutator.

## Goal

A ship may install a `RemoteControl` module. It is a **standalone module**, not
a second commutator and not another way to drive `SessionMux`.

The player talks to RemoteControl like any other module (one session opened on
the **host** ship's commutator). RemoteControl itself owns the table of tunnels
to other ships. A command for a remote ship is sent **to RemoteControl**; the
module strips its header (`tunnel_id`), and hands the remainder to the **target
ship's commutator**. Replies take the same path in reverse.

The module enforces two blueprint limits:

1. maximum number of active remote connections;
2. maximum distance to the remote ship.

If the remote ship leaves that distance, RemoteControl drops that tunnel and
stops forwarding.

## Proposed behavior

### Interface

`IRemoteControl` is a new protobuf interface. Rough shape (field numbers are
illustrative):

```protobuf
message IRemoteControl {
  enum Status {
    SUCCESS              = 0;
    SHIP_NOT_FOUND       = 1;
    SHIP_TOO_FAR         = 2;
    TOO_MANY_CONNECTIONS = 3;
    INVALID_TUNNEL       = 4;
  }

  message Specification {
    uint32 max_connections = 1;
    uint32 max_distance_km = 2;
  }

  oneof choice {
    bool    specification_req = 1;
    string  open_tunnel       = 2;  // ship name
    uint32  close_tunnel      = 3;
    bool    connections_req   = 4;
    Message encapsulated      = 5;  // data plane: Message.tunnelId is RC's id

    Specification specification       = 21;
    uint32        open_tunnel_report  = 22;
    Status        open_tunnel_failed  = 23;
    Status        close_tunnel_status = 24;
    uint32        connections         = 25;
    Message       from_remote         = 26;  // replies, same wrapping
  }
}
```

Commands (control plane, `IRemoteControl` on the module session):

1. **specification_req** — ignored bool; reply is `specification`.
2. **open_tunnel(name)** — open a tunnel to the player's ship with that
   `module_name`. Reply is `open_tunnel_report` with a `tunnelId` that belongs
   to **this module**, or `open_tunnel_failed` with a status.
3. **connections_req** — reply is the number of tunnels this module currently
   holds.
4. **close_tunnel(tunnelId)** — drop an entry in RemoteControl's table and
   stop forwarding. Needed so the connection limit is usable without closing
   the session to the module itself.

`close_tunnel` is RemoteControl closing **its** tunnel, not
`ICommutator.close_tunnel` and not `SessionMux::closeSession` on a session
bound to the remote ship.

When a tunnel dies for an external reason (range, destroy, remote offline),
RemoteControl notifies the client on the module session (e.g.
`close_tunnel_status` / `INVALID_TUNNEL`) and must not keep forwarding.

### Specification

| Field             | Meaning                                              |
|-------------------|------------------------------------------------------|
| `max_connections` | Hard cap on tunnels this module may hold at once     |
| `max_distance_km` | Max distance from the **host** ship to the remote    |

Both come from the blueprint. They do not change at runtime.

A connection stays up while distance **≤** `max_distance_km`. Strictly greater
drops it.

### Not a commutator

`ICommutator.open_tunnel(slot)` asks `SessionMux` to bind a child session to
the module in that slot. After that, `Message.tunnelId` is a mux session id:
the commutator never sees those messages again.

RemoteControl does **not** work that way. It must see every command for a
remote ship, because it owns the connection table and the range check. Do not
implement `open_tunnel(name)` as `SessionMux::createSession(..., pShip)` (or
the ship's commutator) so that later traffic bypasses the module.

The `tunnelId` it returns is an id in **RemoteControl's** namespace, unique
among this module's connections. It is not a `SessionMux` session id and not a
commutator slot.

### Forwarding

The client has one SessionMux session to the RemoteControl module (opened on
the host ship, like a session to an engine). All of the following stay on
that session.

**Control:** `IRemoteControl` payloads (`specification_req`, `open_tunnel`,
`close_tunnel`, `connections_req`).

**Data:** `encapsulated` / `from_remote` — a nested `Message` whose `tunnelId`
is the id RemoteControl returned. RemoteControl always receives this payload
on its module session.

On a data message RemoteControl:

1. Reads `tunnelId`, looks it up in its table. Unknown id → fail, do not
   forward.
2. Strips that header.
3. Passes the remaining message to the **target ship's commutator**.

The reverse path: the remote commutator's reply goes to RemoteControl, which
puts the same `tunnelId` back on and sends it to the client on the module
session.

The inner payload is whatever the player would send to that ship's commutator
(`ICommutator` to list modules and open further tunnels to devices on that
ship). RemoteControl does not interpret it.

### Opening a tunnel

Lookup is by **exact, case-sensitive ship name** among ships **owned by the
same player**. Do not look up through the root commutator's slot list: that
list is the thing this module is meant to replace later.

On `open_tunnel(name)`:

1. Resolve the name to a live ship of this player. Missing, empty, or
   ambiguous name → `SHIP_NOT_FOUND`. Another player's ship is not found.
2. If the ship is farther than `max_distance_km` → `SHIP_TOO_FAR`.
3. If the module already holds `max_connections` tunnels →
   `TOO_MANY_CONNECTIONS`.
4. Otherwise add an entry to RemoteControl's table (name / ship / commutator)
   and return that entry's id as `open_tunnel_report`. No mux session is
   bound to the remote ship.

The host ship is a valid target if it is in range (distance 0). Opening a
second tunnel to a ship that already has one is allowed, subject to the cap.

### Range enforcement

On the module's `proceed` tick, drop every table entry whose remote ship is
gone or whose distance exceeds `max_distance_km`. Notify the client; further
data messages with that `tunnelId` must not be forwarded.

### Ownership and identity

- Only the owner's ships. Foreign / hostile control is out of scope.
- Names: SES-207 makes attached ship names unique per player. Until that
  ships, if two of the player's ships share a name, `open_tunnel` fails with
  `SHIP_NOT_FOUND` rather than picking one at random.
- `slot_id` on a commutator is not an argument of this API. The point of the
  module is name-based reach without a global slot table.

## Why not the alternatives

- **Keep using the root commutator for this.** It has no range and no
  connection cap, and it is the hub this module exists to replace.
- **Open by `slot_id`.** Slots are local to a commutator. After the root hub
  is gone there is no global slot for "that other ship".
- **Open by `ship_id`.** Clients discover ships by name; SES-207 is what makes
  that name unique among a player's live ships.
- **Bind a `SessionMux` child session to the remote ship (or its
  commutator).** Then `Message.tunnelId` is mux routing, RemoteControl never
  sees the command, and it cannot enforce range or the connection table on
  live traffic. That is "another commutator", which this module is not.
- **Omit `close_tunnel`.** The only way to free a slot would be to close the
  RemoteControl session (losing every link) or wait for the remote to leave
  range.

## Consequences (not this task)

Once every ship the player wants to fly has a RemoteControl (or the player
always logs into the ship they want):

1. Ships no longer need to be attached to the root commutator.
2. Therefore a ship no longer needs to be a `BaseModule` just so the root hub
   can open a session to it.
3. Login can bind the UDP session to one ship's commutator instead of a
   player-level hub.

None of that is required here. Ships stay on the root commutator. RemoteControl
is additive.

## Scope

- `server/Protocol.proto` — `IRemoteControl` and a `Message` oneof field.
- `server/Modules/RemoteControl` — module, manager, dispatch from
  `BaseModule`; the module owns the tunnel table and the forward/strip path
  to the target ship's commutator. Do not reuse `Commutator::onOpenTunnelRequest`.
- `server/Blueprints/Modules` — blueprint with `max_connections` and
  `max_distance_km`; register in `BlueprintsFactory`.
- A way to resolve "player's ship by name" that does not go through the root
  commutator's slots (e.g. `GlobalContainer<Ship>` filtered by owner, or a
  player-side index). Prefer the smallest hook; do not redesign `Player`.
- `docs/API.ru/IRemoteControl.md` — interface, statuses, range rule,
  strip-and-forward path.
- C++ ClientSDK wrapper and module tests: spec, open-by-name, traffic on the
  tunnel, cap, too far, range drop, close, connection count.
- Python SDK (rpc + module + configurator blueprint) and TypeScript
  lowlevel / midlevel / highlevel / `ModuleType` / factories, plus protobuf
  regenerate.

A default test blueprint is enough; no need to put RemoteControl on every
stock ship.

## Out of scope

- Removing or emptying the root commutator.
- Detaching ships from the root commutator.
- Making `Ship` not a `BaseModule`.
- Changing login so the player session starts on a ship.
- Tunneling to another player's ship.
- Highlevel "fleet" helpers beyond a normal module wrapper.
- Unique ship names (SES-207).

## Acceptance criteria

- A ship with RemoteControl installed answers `specification_req` with the
  blueprint `max_connections` and `max_distance_km`.
- `open_tunnel` with the name of another of the player's ships in range
  returns a `tunnelId` owned by RemoteControl. A nested command with that
  id is received by RemoteControl, stripped, and delivered to that ship's
  commutator (e.g. `ICommutator` listing that ship's modules).
- Traffic to a remote ship does **not** bypass RemoteControl: there is no
  mux session bound to the remote ship for this feature.
- `open_tunnel` with an unknown name, another player's ship name, or an empty
  name fails with `SHIP_NOT_FOUND`.
- `open_tunnel` to a ship farther than `max_distance_km` fails with
  `SHIP_TOO_FAR` and does not consume a connection slot.
- Opening more than `max_connections` tunnels fails with
  `TOO_MANY_CONNECTIONS`; existing tunnels stay up.
- `connections_req` reports the current number of held tunnels.
- `close_tunnel` frees a slot; a later `open_tunnel` can reuse the capacity.
- If the remote ship moves beyond `max_distance_km`, RemoteControl drops the
  table entry, notifies the client, and does not forward further data with
  that `tunnelId`.
- Ships remain attached to the root commutator; existing root-commutator
  tunnels to ships still work.
- Docs describe the three client-facing calls, `close_tunnel`, the two spec
  fields, the range-drop rule, and the strip-and-forward path (RemoteControl
  is not a commutator).
- C++ autotests cover the cases above.
