# SES-213: TypScript SDK: Preempt long-running module operations

## Background

A player’s control loop does not wait politely. It changes its mind: abort
the burn, leave this asteroid, send the ship somewhere else.

Highlevel operations that run for a long time — following a flight plan,
mining, building a ship — complete only when the work finishes or when the
module is torn down. There is no way to stop *this* job and keep the same
engine, miner, or shipyard.

The harvester’s “interrupt” therefore cannot actually preempt a flight. It
cancels the client’s own sleep; the SDK keeps waiting on the server until
the module is torn down. That is too blunt for control: the next command
needs the same module, not a new one.

## Require

Change the contract of long-running highlevel operations so a caller can
stop work already in flight without releasing the module.

After a stop, the same module must be usable for a new command. How stop
is requested is left open.

## Acceptance

- While a ship is following a flight plan, the caller can stop that follow
  and set a new thrust on the same engine without releasing the ship or the
  engine.
- While a miner is extracting from an asteroid, the caller can stop that
  job and start another on the same miner without releasing it.
- A stop that the caller requested is distinguishable from a module ending
  such as cargo full, and from a lost connection.
