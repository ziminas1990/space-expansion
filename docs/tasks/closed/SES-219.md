# SES-219: Game as a root commutator module

## Background

`IGame` is not a module. It has no slot on the player's root commutator,
no way to open a tunnel to it, and no subscribe. The only payload is an
unsolicited end-of-game report. The server still does not have a place
to send that report: broadcasting it on commutator sessions is unfinished.

Clients cannot find Game the way they find SystemClock, Messanger, or
the blueprints library. They either wait on a commutator session that
is not an `IGame` channel, or they omit Game entirely.

A player should attach to Game like any other root module and listen
for match updates there.

## Require

Make Game a first-class module on each player's root commutator, the
same kind of object as SystemClock:

- it appears among the attached modules;
- a tunnel to that slot speaks `IGame`;
- it is not a ship and is not built or spawned.

Add a `monitor` command. After the client sends `monitor` on a
dedicated session, the server sends game updates on that session.
That is how a player hears about the match, including the end-of-game
result that exists today. Do not deliver those updates on a commutator
session.

Client SDKs expose Game as a slot module with monitoring, following
the same pattern they use for SystemClock.

Document the Game interface.

## Acceptance

- After login, the root commutator lists a Game module. Opening a
  tunnel to that slot yields `IGame`, not `ICommutator`.
- A client that sends `monitor` on that tunnel receives game updates
  on the same session. When the match ends, that includes the
  end-of-game result.
- Closing the monitoring session stops updates for that client.
  Other monitors on the same Game keep receiving them.
- Game-over is not sent as an unsolicited `IGame` payload on a
  commutator session.
- SDKs can open Game from the root commutator and subscribe to
  updates without a special root-session path.
- The Game interface is documented.
- Existing login, root modules, and commutator traffic keep working.
