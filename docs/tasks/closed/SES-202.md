# SES-202: Separate Ship module type from its blueprint name

## Problem

`Ship` is the only module whose runtime `module_type` includes the blueprint
variant:

```text
Ship/Civilian-Miner
```

For every other module, `module_type` identifies the supported interface
(`Engine`, `ResourceContainer`, and so on), while the blueprint is a separate
domain concept.

This exception requires prefix parsing and special types in the SDKs, and makes
`module_type` serve both as interface identity and blueprint metadata.

## Goal

Use the fixed runtime type `Ship` for every ship and expose the blueprint name
separately through `ICommutator.ModuleInfo`.

```text
module_type:    Ship
module_name:    Miner-1
blueprint_name: Ship/Civilian-Miner
```

`slot_id` remains the primary runtime identity of an attached module.

## Proposed behavior

1. Add an optional `blueprint_name` field to `ICommutator.ModuleInfo`.
2. A ship reports `module_type = "Ship"` and its full blueprint name in
   `blueprint_name`.
3. Commutator module-info responses and attach updates include this metadata.
4. SDK factories select the ship interface using an exact `Ship` match instead
   of parsing the `Ship/` prefix.
5. SDK registries must not assume that `(module_type, module_name)` is unique.
   Ships with the same name but different blueprints must not overwrite each
   other; use `slot_id` as the primary key.
6. Blueprint APIs, Shipyard requests, administrator spawn requests, and player
   persistence continue using full blueprint names such as
   `Ship/Civilian-Miner`.

`blueprint_name` is discovery metadata. It must be available without opening a
tunnel to the ship or performing an additional specification request.

## Compatibility and migration

Roll out the change in stages:

1. Add `blueprint_name` while the server still reports legacy
   `module_type = "Ship/<variant>"`.
2. Update SDKs to consume `blueprint_name` and accept both legacy
   `Ship/<variant>` and the new fixed `Ship` type.
3. Change the server to report `module_type = "Ship"`.
4. Remove legacy SDK fallback in a later cleanup after old servers are no
   longer supported.

Adding the protobuf field is wire-compatible, but changing the meaning of
`module_type` is a semantic breaking change for clients that only recognize
the `Ship/` prefix.

## Scope

- `server/Protocol.proto` — add `ModuleInfo.blueprint_name`.
- `server/Modules/Ship` — store blueprint identity separately and use the fixed
  module type `Ship`.
- `server/Blueprints/Ships` — pass the full blueprint identity to built ships.
- `server/Modules/Commutator` — populate blueprint metadata in module-info
  responses and attach updates.
- Server ClientSDK, functional tests, and protocol documentation.
- Python SDK factories, module registry, ship lookup helpers, tests, demo, and
  web-client integration.
- TypeScript lowlevel, midlevel, and highlevel factories, module types,
  registries, player discovery, and tests.

## Out of scope

- Renaming blueprint identifiers used by BlueprintsLibrary, Shipyard, or the
  administrator API.
- Changing player save keys such as `Civilian-Miner/Miner-1`.
- Requiring `IShip.Specification` to discover a ship's blueprint.

## Acceptance criteria

- Every newly reported ship has `module_type == "Ship"`.
- Every ship's `ModuleInfo.blueprint_name` contains its full blueprint name,
  for example `Ship/Civilian-Miner`.
- Ship discovery does not require opening a tunnel or requesting a
  specification.
- SDK factories no longer require `startsWith("Ship/")` after legacy fallback
  is removed.
- Two attached ships with the same `module_name` do not overwrite each other in
  an SDK registry.
- Blueprint lookup, Shipyard construction, administrator spawn, and existing
  player save loading continue to use the existing blueprint naming scheme.
- Server, Python SDK, and TypeScript SDK tests cover both the migration path and
  the final fixed-type behavior.
