# SES-207: Guarantee unique ship names per player

## Problem

A player can own several ships with the same `module_name`. Shipyards do not
check the name when a ship is attached, and administrator spawn does not
check it either. Two shipyards can finish two ships with the same requested
name; the player then has two attached ships that cannot be told apart by
name.

Destroying one of the finished ships, or reporting `BUILD_FAILED` for a ship
that already exists, is not an acceptable outcome.

SES-202 therefore treats `slot_id` as the only reliable identity and forbids
SDKs from assuming that `(module_type, module_name)` is unique for ships.

## Goal

Among ships **already attached** to a player's root commutator, `module_name`
is unique.

The player may order any number of builds with the same name. In-progress
jobs do not occupy a name. When a ship is attached, if its name collides
with an already attached ship, the **new** ship is renamed. The existing
ship is never renamed, destroyed, or failed.

Uniqueness is per player, not global. Two players may both have a ship named
`Miner-1`.

## Proposed behavior

No name registry, no reservation at `start_build`. Collision handling lives
in the attach path (`Player::onNewShip`), so shipyard completion, administrator
spawn, tests, and load all share it.

### When a ship is attached

1. If the ship's name is empty, reject attach / do not start a build that
   would produce an empty name. Do not invent a name from nothing.
2. If no attached ship of this player already has that name, attach as-is.
3. Otherwise rename the **new** ship (see suffix rule), then attach.

Check-and-rename-and-attach must be atomic on the player: two shipyards can
`proceed` on different conveyor threads and both call `onNewShip` at once.

Collide against other **ships** on the player's root commutator, not against
system modules (`SystemClock`, `Messanger`, blueprints storage). Comparison
is exact, case-sensitive string equality.

There is no occupied-name table to maintain on destroy, cancel, or
`BUILD_FAILED`. A destroyed ship's name is free because it is no longer
attached.

`BaseModule` needs a way to change `m_sModuleName` before the ship is
published on the commutator, so `ModuleInfo` reports the final name.

### Suffix rule

Let `S` be the ship's name at attach time (the name requested at
`start_build` / spawn).

If `S` contains at least one ASCII space (`U+0020`):

```text
S + " " + N     →  "Sweet Home 1"
```

Otherwise:

```text
S + "-" + N     →  "Scout-1"
```

`N` is the smallest integer **greater than zero** such that the resulting
string is not used by any attached ship of this player. There is no `N = 0`.

Do not parse or strip an existing numeric suffix. Tabs and other whitespace
do not count as a "space" for choosing `-` vs ` `.

| Occupied                    | Requested    | Assigned         |
|-----------------------------|--------------|------------------|
| —                           | Scout        | Scout            |
| Scout                       | Scout        | Scout-1          |
| Scout, Scout-1              | Scout        | Scout-2          |
| Scout-1                     | Scout        | Scout            |
| Scout-1                     | Scout-1      | Scout-1-1        |
| Sweet Home                  | Sweet Home   | Sweet Home 1     |
| Sweet Home, Sweet Home 1    | Sweet Home   | Sweet Home 2     |
| Drone #1                    | Drone #1     | Drone #1 1       |

### Shipyard

`start_build` is unchanged: accept a duplicate name, start building under
the requested name.

When `finishBuildingProcedure` calls `onNewShip`, the ship may come back
with a different name. `building_complete.ship_name` **must** be that final
name, not the original request. Completion never fails because of a name
clash.

Empty `ship_name` on `start_build` should still be rejected (the attach
path must not have to invent a base name).

### Administrator spawn

Same attach path. A taken name is not a spawn error: the ship is created
with the suffixed name. The client discovers it from commutator `ModuleInfo`
(spawn returns `ship_id`). Empty names still fail.

### Persistence and load

`Player::load` already calls `onNewShip`. Duplicate names in a save are
suffixed rather than failing the load. A well-formed save is unchanged.

### Destruction

No extra hook. Once the ship is detached, its name may be reused by the
next ship that attaches with that base name. A rebuilt ship with the same
name is a different object (same as today's `ModuleRegistry` comment).

## Why not the alternatives

- **Reserve the name at `start_build`.** Prevents the player from queueing
  several "Scout" jobs, and needs release on cancel / fail / destroy for
  names that are not yet visible on the commutator. Unnecessary once
  uniqueness is defined only among attached ships.
- **Reject `start_build` with `SHIP_NAME_IN_USE`.** The player chose a
  repeated name on purpose; the server should still build the ship.
- **Fail or destroy at completion.** The ship already exists as a world
  object and resources are spent.
- **Parse a trailing number and increment it.** Ambiguous
  (`Scout-1-1` vs `Scout-2`) and surprises a player who asked for the
  literal name `Scout-1`. Always append a new separator + `N` to `S`.

## Consequences

Once attached ships of one player have unique names:

1. TypeScript `ModuleRegistry` can key attached ships by name the same way
   it keys other modules (`type::name`). The `is_reusable_wrapper` exception
   for `SHIP` can be dropped **or** kept only as an object-identity choice
   after destroy-and-rebuild, not because two live ships can share a name.
2. Clients can treat `module_name` as a unique identifier for a **live**
   ship even when the slot is unknown. `slot_id` remains the runtime
   attachment key for tunnels.
3. The name sent in `start_build` may differ from the attached ship's
   `module_name`. Lookups must use `building_complete` / `ModuleInfo`.

SDK registry simplification is a follow-up, not a requirement of this task.
SES-202 item 5 ("registries must not assume `(module_type, module_name)` is
unique") is superseded for **attached** ships of one player once this ships.

## Scope

- `world::Player::onNewShip` — atomic uniquify-and-attach with the space /
  hyphen suffix rule.
- `server/Modules/BaseModule` — allow renaming before attach if the name is
  currently immutable.
- `server/Modules/Shipyard` — pass the final name in `building_complete`;
  reject empty names on `start_build`.
- `docs/API.ru/IShipyard.md` — document that the attached name may gain
  `-{N}` or ` N`, and that `building_complete.ship_name` is authoritative.
- Administrator spawn inherits the behavior via `onNewShip`.
- C++ shipyard / spawn tests for the suffix table, two yards completing the
  same requested name, and reuse after the occupying ship is gone (if a
  destroy path is testable).
- Python / TypeScript protobuf regenerate only if a new field or status is
  added (not required if `building_complete.ship_name` already carries the
  final name).

## Out of scope

- A player-level occupied-name registry or reservation at `start_build`.
- Implementing `cancel_build`.
- Unique module names on a ship's own commutator.
- Unique names across players.
- Unique ship names vs non-ship modules on the root commutator
  (`Messanger`, `SystemClock`).
- Rewriting TypeScript `ModuleRegistry` to key ships by name (follow-up).
- Changing `ICommutator.ModuleInfo` or making `slot_id` optional.

## Acceptance criteria

- `start_build` with a name that another attached ship already uses is
  accepted and builds.
- Two shipyards of the same player may both start with the same requested
  name.
- When the first of those builds completes, the ship is attached with the
  requested name. When the second completes, it is attached as
  `{name}-1` or `{name} 1` according to the suffix rule, never as a
  duplicate, and never as `BUILD_FAILED`.
- `building_complete.ship_name` is the name actually attached to the
  commutator.
- Administrator spawn of a ship with an occupied name succeeds with a
  suffixed name.
- Empty ship names are rejected at `start_build` / spawn.
- Two different players can still use the same ship name.
- After an occupying ship is destroyed, a new ship may take the original
  name again.
- Docs for `IShipyard` describe the suffix rule.
- Server autotests cover the suffix table (including the space vs hyphen
  split) and two yards completing the same requested name.
