# SES-233: Add Shipyard monitoring

## Background

`IShipyard` reports build progress on the session that sent `start_build`.
Another client can open a Shipyard session, but it cannot learn whether a
build is already running, which blueprint and requested name it uses, or how
far it has advanced. The tactical map needs that information for
[TSSDK-008](../../../typescript-sdk/tasks/closed/TSSDK-008.md).

## Require

Add a `monitoring` command to `IShipyard`. A client sends it on a Shipyard
session to observe that Shipyard's builds without starting or changing one.

The server immediately sends `monitoring_ack` on that session. If a build is
in progress, the next monitoring event is `BuildStarted` for that build,
followed by a `building_report` with its current progress and status.
If the Shipyard is idle, the acknowledgment is followed by no build event
until a build starts.

The monitoring stream sends these events in order for each build:

- `BuildStarted` when a build starts. It identifies the blueprint type and
  the requested ship name. For a build already underway when monitoring
  starts, the following `building_report` supplies the current progress and
  building or frozen state, so a new subscriber can display it immediately.
  A successful `start_build` also receives this message as its immediate
  response. Rejected starts still receive their failure status in
  `building_report`.
- Existing `building_report` messages while the build runs. Each gives the
  current fraction complete and its `BUILD_IN_PROGRESS` or `BUILD_FROZEN`
  status. A final `BUILD_FAILED` report ends a build that does not produce a
  ship. Progress uses the existing 0–1 scale.
- Existing `building_complete`, carrying `ShipBuilt`, when the finished ship
  is attached to the player's commutator. It gives the assigned ship name
  and slot ID. The stream stays active for later builds.

Monitoring is per session. Multiple clients can monitor the same Shipyard;
closing one monitoring session removes only that subscriber. Existing
`start_build` responses and build reports keep working for the builder.
Document the command and events in `docs/API/shipyard.md`.

## Acceptance

- `monitoring` receives `monitoring_ack` first, including when the Shipyard is
  idle. An idle Shipyard sends no `BuildStarted` until a build starts.
- Joining during a build receives `monitoring_ack`, then `BuildStarted` for
  the current build with its blueprint and requested name, then a
  `building_report` with current progress and advancing or frozen status.
- A monitor present before a build receives `BuildStarted`, subsequent
  progress or frozen updates, and `ShipBuilt` in that order.
- A successful `start_build` receives `BuildStarted` as its first reply, with
  the blueprint and requested name. A failed start receives a failure
  `building_report`.
- A failed build sends its terminal status, after which the monitor can
  observe a later build on the same session.
- Two monitoring sessions receive the same build events independently.
  Closing one leaves the other and the active build unaffected.
- Existing clients using `start_build` still receive their build reports and
  completion response.
- `docs/API/shipyard.md` describes the monitoring command, initial state,
  event fields, and message order.
