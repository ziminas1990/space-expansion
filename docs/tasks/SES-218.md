# SES-218: IEngine monitoring for thrust vector changes

## Background

`IEngine` can report the current thrust (`thrust_req` / `thrust`) and accept
a new vector (`change_thrust`), but it has no subscription. A client that
needs to know when thrust actually changes must poll.

That is not enough. Thrust changes without a new command: a burn with
`duration_ms` ends and the vector goes to zero; a command with
`Message.timestamp` is applied later; the server clamps magnitude to
`max_thrust`. `change_thrust` stays fire-and-forget (SES-201). The way to
observe the applied vector is a monitoring session, the same pattern as
`IResourceContainer` and `ICommutator`: subscribe once, then receive
indications when the value changes.

## Require

Add event-driven monitoring to `IEngine` in `server/Protocol.proto`. It is
not a periodic clock like `IShip.monitor` / `ISystemClock.monitor`. The
server sends a notification when the **applied** thrust vector changes.

Reuse `CurrentThrust` (`thrust`) as the indication. Do not put the update
on the `change_thrust` session.

Illustrative shape (keep existing field numbers; `monitor` is new):

```protobuf
message IEngine
{
  message Specification {
    uint32 max_thrust = 1;
  }

  message ChangeThrust {
    double x           = 1;
    double y           = 2;
    uint32 thrust      = 4;
    uint32 duration_ms = 5;
  }

  message CurrentThrust {
    double x      = 1;
    double y      = 2;
    uint32 thrust = 4;
  }

  oneof choice {
    bool         specification_req = 1;
    ChangeThrust change_thrust     = 2;
    bool         thrust_req        = 3;
    bool         monitor           = 4;

    Specification specification = 21;
    CurrentThrust thrust        = 22;
  }
}
```

Behavior:

1. The client sends `monitor` on a dedicated session. After that, the
   server sends `thrust` on that session.
2. The first `thrust` is the vector in effect at subscribe time (a
   snapshot). Later `thrust` messages are sent only when the applied
   vector changes: direction (`x`, `y`) or magnitude (`thrust`).
3. Notify when `change_thrust` is **applied** (including a delayed
   `Message.timestamp`, including clamp to `max_thrust`), and when a
   timed burn expires and the vector becomes zero.
4. Do not notify if a new command leaves the applied vector unchanged.
5. Several sessions may monitor the same engine. Closing a session stops
   that subscription only.
6. `change_thrust`, `thrust_req`, and `specification_req` are unchanged.

Python SDK and TypeScript SDK must expose this monitoring. Follow the
existing monitoring style in each SDK (`ResourceContainer` /
`PassiveScanner`): Python async generator, TypeScript midlevel
`monitoring()` on a dedicated session. TypeScript highlevel should let a
caller observe thrust changes without talking to the protocol (events or
an equivalent, as with cargo / scanner).

Document the new request and the notification rule in
`docs/API.ru/IEngine.md`.

## Acceptance

- After `monitor`, the client receives a `thrust` snapshot, then a
  `thrust` indication each time the applied vector changes, and not when
  it does not.
- A `change_thrust` that is applied (including clamp and delayed
  timestamp) produces a monitoring indication with the vector that is
  actually in effect.
- When `duration_ms` elapses, monitors receive a zero-thrust indication
  without a further client command.
- `change_thrust` still does not wait for a reply on its own session.
- Python and TypeScript SDKs can subscribe and receive those updates.
- `docs/API.ru/IEngine.md` describes monitoring.
- Server autotests cover subscribe, applied `change_thrust`, duration
  expiry, and no-notification when the vector is unchanged.
- Existing `specification_req` / `thrust_req` / `change_thrust` clients
  keep working.
