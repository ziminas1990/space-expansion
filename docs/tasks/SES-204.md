# SES-204: Add a heartbeat interval to midlevel `monitoring()` callbacks

## Problem

Midlevel `monitoring()` loops invoke a client callback and stop when the
callback returns `false`. That stop path only runs after the next wait
completes, so the callback must fire regularly even when the server sends no
updates. Otherwise client code that sets a stop flag cannot exit until the next
real update (or until a hardcoded wait expires).

Callers cannot choose that cadence today:

- `Commutator.monitoring` waits via `wait_update()` with the lowlevel default
  of 500 ms.
- `ResourceContainer.monitoring` and `PassiveScanner.monitoring` hardcode
  200 ms.
- `Ship.monitoring(update_ms, …)` and `SystemClock.monitoring(interval_ms, …)`
  send that value to the server as the update period. It is not the client wait
  timeout. `Ship` then waits with the lowlevel default of 500 ms and treats a
  timeout as a monitoring failure. `SystemClock` computes a long wait timeout
  and **skips** the callback on timeout, so a stop flag is ignored until the
  next tick arrives.

## Goal

Every midlevel `monitoring()` function takes an extra parameter,
`heartbeat_ms`, that is the maximum time to wait for a server update before
invoking the callback anyway.

The same value is passed down to the corresponding lowlevel `wait_*` call as
its timeout.

## Proposed API

Name: **`heartbeat_ms`**. It is a client-side wait, not a server update period.
Do not reuse `interval_ms` / `update_ms` — those already mean “how often the
server should send updates” on `Ship` and `SystemClock`.

Add it as a trailing parameter with a default (200 ms, matching the existing
hardcoded waits) so current call sites keep compiling:

```ts
// modules without a server period
monitoring(callback, heartbeat_ms = 200)

// modules that already send a period to the server
monitoring(update_ms, callback, heartbeat_ms = 200)
monitoring(interval_ms, callback, heartbeat_ms = 200)
```

On wait timeout:

1. Do not treat timeout as a monitoring error.
2. Invoke the callback (with the last snapshot, `undefined`, or an empty list —
   keep each module’s current idle payload).
3. If the callback returns `false`, leave the monitoring loop.
4. Otherwise wait again.

A real update still invokes the callback immediately, without waiting for the
heartbeat to elapse.

## Scope

TypeScript SDK only.

- Midlevel: `Commutator`, `ResourceContainer`, `PassiveScanner`, `Ship`,
  `SystemClock` — add `heartbeat_ms` and pass it to lowlevel waits.
- Lowlevel waits that monitoring uses but that do not yet accept a timeout
  (notably `Ship.wait_state`) must take one.
- Highlevel call sites that already run a stop-flag callback
  (`module_registry`, `ship`, `resource_container`, `passive_scanner`,
  `system_clock`) should pass an explicit `heartbeat_ms` where the default is
  too coarse for a timely `release()`.
- Tests that exercise monitoring stop/idle behavior.

## Out of scope

- Changing how often the server generates updates (`update_ms` / `interval_ms`).
- Python SDK, protocol, or server changes.
- Highlevel public APIs, except where they must pass `heartbeat_ms` through to
  midlevel.

## Acceptance criteria

- Every midlevel `monitoring()` accepts `heartbeat_ms` and uses it as the
  lowlevel wait timeout.
- With no server updates, the callback runs at about that interval and can stop
  the loop by returning `false`.
- `Ship` and `SystemClock` keep their existing server-period argument; it is
  not reused as the heartbeat.
- `SystemClock` invokes the callback on wait timeout instead of swallowing it.
- `Ship` monitoring no longer fails when a state update takes longer than 500 ms.
- Existing callers that omit `heartbeat_ms` still compile and keep the 200 ms
  default.
- TypeScript SDK tests covering monitoring idle/stop pass.
