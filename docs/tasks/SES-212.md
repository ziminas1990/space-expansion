# SES-212: Distinguish module outcomes from transport failure

## Background

A player driving ships from the TypeScript highlevel API often needs to
branch on *why* an operation ended. These are normal module answers:

- cargo full,
- asteroid out of range,
- shipyard already building.

A dropped session is not.

Today those answers collapse into the same failure object as a timeout or a
broken channel. The only way to tell them apart is to parse a human-readable
message. The headless harvester does exactly that: it treats cargo-full as
success by searching the error text.

That is not an API a player can program against. Control logic has to guess
whether it should retry, pick another asteroid, or give up.

## Require

Change the highlevel contract so a module’s own outcome is a first-class
result, distinct from SDK or transport failure.

A caller must be able to branch on that outcome without inspecting message
strings. How the result is represented is left open.

## Acceptance

- After mining until the bound cargo cannot take more ore, a caller can tell
  that ending from a lost connection without reading error text.
- The same distinction exists for other module-specific endings a control
  loop actually uses, such as an asteroid that is too far or a shipyard that
  is already building.
- Transport and SDK failures remain recognizable as failures, not as one of
  those module endings.
