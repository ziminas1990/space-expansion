# SES-215: TypScript SDK: Bind operation progress to a single call

## Background

Some highlevel objects publish a stream of updates for as long as they
exist. That fits a cargo hold or a scanner: the world keeps changing.

It does not fit a job. Mining one asteroid is a single call with a start
and an end. Progress of that job belongs to that call. Today the reports
live on the miner object instead. The call that starts mining does not
take a per-job listener, so the harvester subscribes globally and must
unsubscribe by hand. Sequential jobs on the same miner can mix reports, or
leak listeners, unless the client is careful.

A player writing a control loop should not have to manage the object’s
lifetime in order to hear about one extraction.

## Require

Change the contract of one-shot long operations so progress and
stop-for-this-job belong to that invocation, not to the module for its
whole life.

Object-level streams may still exist where they describe ongoing state.
The shape of a per-call progress API is left open.

## Acceptance

- Two mining jobs run one after another on the same miner, each with its
  own progress handler, do not receive each other’s reports.
- A progress handler installed for one job does not stay attached after
  that job ends unless the caller asked for a lasting subscription.
- The caller can still observe ongoing state of a module that is not a
  job (for example cargo content) without tying that stream to a single
  call.
